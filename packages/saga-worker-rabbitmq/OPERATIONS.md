# Saga commit intake (redemeine-fyp3.4)

Configure one dedicated RabbitMQ vhost **per environment** in the operator-supplied AMQP URL. Within that vhost, provision the stable names `rdm.saga.commits` (incoming durable queue), `rdm.saga.commits.dlq` (durable dead-letter queue), and `rdm.saga.commits.dlx` (durable direct dead-letter exchange). Do not suffix queue names with the environment or share this queue with another independently consuming projection/saga service: competing consumers would divide commits rather than each receiving a copy. If independent services need every commit, plan separate bound queues in a separate issue. Renaming an existing durable queue requires an explicit drain/migration plan; provisioning does not delete or repair existing declarations.

Supply the deployed Tapeworm dispatcher **headers** exchange name, exact `collection` and nonempty `partitions` to `createSagaCommitQueueTopology`. Supply `tenant` only when it exactly matches the configured `publisherTenant`; the binding uses `x-match=all` with `collection`, `partitionId`, and optional `tenant`. No `aggregateType` header is published or matched. Verify the upstream exchange configuration and publisher headers for the deployment. The source exchange belongs to the publisher: `provisionSagaTopology` asserts compatible durable headers declarations, not a new publisher contract. Broker precondition/permission errors must stop startup; use a fresh channel after a declaration failure, never consume until provisioning succeeds on that connection. Pass the returned `worker.queue` and `worker.source` to the worker on the same channel. Re-provision after reconnect, before starting the consumer.

Only messages published after a binding exists will be routed to the new queue; this does **not** recover historical commits published before provisioning. Invalid deliveries are subject to the existing worker's poison policy. Permanent failures NACK to the DLQ; transient failures currently NACK with `requeue: true` immediately. `rdm.saga.commits.retry` is **reserved for redemeine-fyp3.5 and is not asserted or used here**. No bounded delay, replay, exactly-once guarantee, or persistence-before-binding guarantee is claimed. Inspect DLQ entries and plan safe replay separately; do not auto-delete old queues or bindings.
